# 移动端客户端架构

写于 2026-09-01。定的是「同一份前端跑在三个壳里」这件事怎么分层，以及移动端最难的
那个问题——数据怎么到手机上——有哪几条路、先做哪条。

## 三个壳，一份前端

```
                    src/  (React + TS，唯一一份)
                      │
        ┌─────────────┼─────────────┐
        │             │             │
    Tauri         浏览器        Capacitor
   桌面客户端       网页版       Android 客户端
   Windows        任意          手机/平板
        │             │             │
   明文文件目录    IndexedDB     IndexedDB（暂）
```

桌面端继续 Tauri（已拍板），移动端 Capacitor、**只做 Android，不做 iOS**（已拍板）。
两个壳都吃 `dist/`，所以顺序永远是 `npm run build` 再 `npx cap sync android`；
`npm run android:sync` 把这两步绑在一起了，别单独跑 sync。

判环境走 `src/lib/runtime.ts`：`detectRuntime()` 返回 `web | tauri | capacitor`。
判定靠嗅探壳注入的全局（`__TAURI_INTERNALS__` / `window.Capacitor.isNativePlatform()`），
不 import 任何一边的 SDK——网页版 bundle 不会被拖大，判环境也不用 await 动态 import。

移动端**不是桌面端的裁剪版**。它是同一批数据的另一种读法：桌面端是工作台（导入、
清洗、正则、写回 ST），移动端是读物（躺着重看，顺手打个分、记一句）。功能分级见
`mobile-priorities.md`。

## 能力矩阵

| 能力 | web | tauri | capacitor | 备注 |
|---|---|---|---|---|
| 库存储 | IndexedDB | 明文文件目录 | IndexedDB（暂） | capacitor 的目标形态待定，见下 |
| 选一个目录当库 | ✗ | ✓ | **✗（不是没做，是不成立）** | Android 11+ 只有 SAF 的 URI 授权，没有任意路径读写权 |
| 读写任意路径 | ✗ | ✓ | ✗ | |
| 应用私有目录读写 | ✗ | ✓ | ✓ 未接 | `@capacitor/filesystem` |
| 原生文件选择器 | ✗ | ✓ | 隐藏 input 可用 | Android 上 `<input type=file>` 会弹系统选择器，这条回退是通的 |
| 保存到用户指定路径 | 下载 | ✓ | ✗ | 手机上「导出」的真实语义是分享，不是选路径 |
| 系统分享面板 | ✗ | ✗ | ✓ 未接 | `@capacitor/share`；**这是移动端超出桌面端的能力** |
| 直读 ST 目录 | ✗ | ✓ | ✗ | ST 跑在电脑上，手机上没有那个目录 |
| 写回 ST | ✗ | ✓ | ✗ | 同上 |
| Service Worker | ✓ | 不注册 | 不注册 | 资产随包发，SW 只会让旧资产盖住新包 |
| 系统后退键 | ✗ | ✗ | ✓ 未接 | 得接 `App.addListener('backButton')`，否则按一下直接退出 Activity |

「未接」= 壳有这个能力、代码里留了 TODO(capacitor) 但还没实现。原生能力调用点：
`lib/vault/bootstrap.ts`、`lib/text-file-export.ts`、`lib/register-sw.ts`、
`lib/vault/tauri-fs.ts`。

## 数据层：手机上的数据从哪来

这是移动端唯一的真问题。桌面端的库是「用户选的一个明文目录」，这个前提在 Android
上不成立——不是权限难申请，是 API 形状不同：SAF 授的是按 URI 的权限，重启后要靠
持久化 URI 续期，没有「路径字符串」这个东西。所以移动端要么换一种数据来源，要么
接受一份副本。

三条候选：

### 甲、Syncthing 同步一份到应用私有目录

用户自己在电脑和手机上装 Syncthing，把库目录同步到手机；移动端只读同步下来的那份。

- 优点：库还是明文目录那套结构，`createTauriFs` 的位置换成 Capacitor Filesystem
  就能复用整条后端；双向、增量、不用我们碰网络；用户已有的备份习惯直接接上。
- 缺点：要用户装第三方应用并配一遍（这是最大的门槛）；同步冲突要有说法；
  Syncthing 的 Android 客户端能不能写进我们的应用私有目录得实测（大概要放在
  共享目录再由我们导入，那就退化成乙了）。

### 乙、桌面端导出「阅读包」，移动端导入

桌面端出一个单文件（选中的角色 + 故事 + 立绘，压缩包或单个 JSON），传到手机导入。

- 优点：最省事，两边都不需要新权限；传输方式随用户（微信、网盘、数据线都行）；
  边界清楚——阅读包是只读快照，不存在写回冲突；能顺带解决「只想带三篇上路」
  这个真实需求。
- 缺点：单向、手动、要重复操作；进度和评分留在手机上，回不到桌面端（除非再做反向
  导出）；大库的包会很大。

### 丙、局域网直读桌面端起的服务

桌面端开个本地 HTTP 服务，手机在同一 WiFi 下直连读。

- 优点：零拷贝，永远是最新的；进度评分能实时写回桌面端，双向天然成立。
- 缺点：要求两台设备同时开机同网段——「躺床上看」这个核心场景恰好是电脑关着的时候，
  这一条基本否掉了它作为主路；还要处理配对、鉴权（局域网里裸开一个能读全部
  聊天记录的服务不能接受）、发现（mDNS 或手输 IP）。

### 先做哪条：乙

理由是场景而不是技术优劣。移动端第一优先级是「躺着重看已经存好的故事」，这个场景
里电脑是关着的——丙直接不成立。甲的能力上限最高，但它把第三方应用的安装和配置摞在
用户面前，而这批用户里能配 Syncthing 的是少数；而且它的实现里最不确定的一环
（Syncthing 能不能写进我们能读的目录）恰好是没法在设计阶段拍板的。

乙的形态最小、最独立，且不阻塞另外两条：阅读包的导入端做完之后，甲相当于把「用户
手动传一个包」换成「同步器自动放一个目录」，导入端能复用；丙则是再上一层的增量。
所以顺序是 乙 → 甲 → （丙看有没有人真要）。

第一版阅读包的边界建议：只带**读**要用的东西——角色卡基本信息 + 立绘 + 选中的故事
正文 + 章节标记 + 书签 + 已有的总结。不带预设、世界书、正则规则（那些是编辑期的
东西，移动端不编辑），这样包能小一个量级。

## 目前的实现状态

Capacitor 外壳已搭好并能 `cap sync`，但**里面跑的就是网页版**：`bootVault()` 在
非 Tauri 环境返回 `'web'`，库落在 IndexedDB。这是有意的——在数据通路定下来之前，
IndexedDB 是诚实的：能读、能存进度和评分，不假装有文件库。

也就是说现在装出来的 APK 是个能读 IndexedDB 里数据的空壳，需要先在设备上导入才有
内容。做完乙之后它才真正可用。

## 未决

- 阅读包的具体格式（压缩包还是单 JSON、立绘内嵌还是并列）
- 手机上产生的进度/评分要不要回到桌面端，怎么回
- Android 后退键的行为表（沉浸阅读 → 退沉浸；抽屉开着 → 关抽屉；在故事里 → 回列表）
- 图标和启动图还是 Capacitor 的默认占位（`android/app/src/main/res/`），发版前要换
